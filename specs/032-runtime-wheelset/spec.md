# Feature Specification: Runtime Wheelset — рантайм из официальных колёс (манифест schema 2)

**Feature Branch**: `032-runtime-wheelset`

**Created**: 2026-10-11

**Status**: Blocked-acceptance

> Open gate: T025 installer smoke. T027 (v1.0.1) is historical and superseded by 1.0.2/1.0.5.

**Input**: Ревизия доставки рантайма по плану «универсальный релиз 1.0.0 с развёртыванием»: вместо сборки `.7z`-паков из чистых venv — фиксация официальных pip-колёс (torch, Argos-стек и зависимости) генератором локов (`pip download --only-binary --no-deps` с официальных индексов), манифест schema 2 (`format:"wheels"`, `files[]` с per-file sha256 и размером), клиент `runtime.py` распаковывает колёса пофайлово без `extractall`, релизный пайплайн публикует лок-артефакты вместо `.7z` (`publish-release.ps1`: «packs» → «locks», `SHA256SUMS` без `packs/*.7z`), а UI и документация показывают честные размеры (cu128 ≈ 2.56 ГБ) и источник (PyPI / PyTorch CDN).

## Clarifications

### Session 2026-10-11

- Q: Какую версию приложения выпускаем с schema 2 (манифест адресуется по версии, старый 1.0.0 с .7z не задевается)? → A: 1.0.1; репетиция на теге-кандидате `v1.0.1-rc1` через CI/draft, затем финальный `v1.0.1`.
- Q: Что публикуем ассетами как «локи» (вместо паков .7z)? → A: как в AUTOMATIC1111 — пин-файлы локов версионируются в репозитории (`locks/`), ревью в PR; ассеты релиза — манифест и `packs-linux.json`; CI проверяет воспроизводимость linux-лока (перегенерация совпадает с закоммиченным).
- Q: Что считать «глубокой» проверкой Tier 2 в гейте релиза? → A: полная установка `torch-cpu` во временный каталог и `import torch`; результат кэшируется в `deep.json` по sha256(setup, portable, server, manifest).
- Q: Что делать со старыми скриптами сборки .7z (`build-runtime-packs.ps1`, `build-runtime-pack.py`)? → A: оставить, пометить deprecated (archive-ветка в `runtime.py` остаётся для schema 1).
- Q: Как гарантируем, что вся последовательность работает до сборки и загрузки релиза? → A: локальный сквозной скрипт `scripts/e2e-runtime-local.ps1` (pytest → win-локи → манифест → dev-`--deploy` → frozen portable/server → `publish-release.ps1 -DryRun` + гейт), падает с non-zero при любой ошибке; installer/GPU smoke — на машине разработчика; финальная сборка — только после зелёного E2E и RC-репетиции.
- Q: PyPI-релиз `argostranslate` 1.11.0 жёстко требует stanza→torch (argos-пак стал бы ~216 МБ и тянул torch); как быть? → A: как в AUTOMATIC1111 (`CLIP_PACKAGE`): колесо `argostranslate` собирается генератором из официального git-коммита (там stanza — optional extra) и публикуется одним ассетом релиза; остальные зависимости — с PyPI.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Установка компонента из официальных колёс (Priority: P1)

Пользователь на NVIDIA выбирает в мастере `torch-cu128`: приложение скачивает из манифеста набор колёс с PyTorch CDN (torch, CUDA-библиотеки, зависимости) и PyPI, сверяет sha256 каждого файла, распаковывает их в `runtime/torch-cu128/site-packages`, пишет маркер и активирует пак. После перезапуска LaMa считает на GPU. Битый или недоступный файл не оставляет мусора: `.part` и `.tmp` удаляются, установка либо завершается целиком, либо честной ошибкой с повтором.

**Why this priority**: это ядро фичи — без надёжной пофайловой установки колёс новый способ доставки не существует.

**Independent Test**: фикстурный манифест schema 2 с локальными URL небольших колёс → `download_and_install` ставит пак; импорт из установленного каталога работает; подмена байта в файле валит установку и чистит каталоги.

**Acceptance Scenarios**:

1. **Given** манифест schema 2 с записью `format:"wheels"`, **When** `POST /api/runtime/download`, **Then** файлы скачиваются по одному с общим прогрессом, каждый сверяется по sha256, пак активируется, маркер `pack.json` на месте.
2. **Given** файл из `files[]` изменился на CDN, **When** установка, **Then** sha256 не сходится, файл удаляется, состояние `error` с возможностью повтора, каталог пака не тронут.
3. **Given** два колеса содержат один и тот же путь с одинаковым содержимым, **When** распаковка, **Then** второй файл пропускается (идемпотентно); при разном содержимом — ошибка установки.

### User Story 2 - Генератор локов и манифест schema 2 (Priority: P1)

Сборщик релиза запускает генератор локов: на Windows — локально, для Linux — в CI. `pip download` тянет точные версии колёс из официальных индексов в стейдж, рядом кладутся `requirements.lock` (freeze) и сводка `packs.json` с `files[]` (имя, URL, sha256, размер) и суммарным `size_bytes`. Манифест schema 2 собирается из сводок обеих платформ; сборка детерминирована, CI не ставит torch в venv — только скачивает колёса.

**Why this priority**: без генератора нет ни манифеста, ни воспроизводимости — источник данных для всего остального.

**Independent Test**: на фикстуре пинов генератор скачивает колёса, сводка проходит валидацию (сумма, sha256, размеры), повторный запуск даёт тот же набор файлов; CI-смоук Linux после установки делает `import torch`.

**Acceptance Scenarios**:

1. **Given** пины из freeze, **When** `pip download --only-binary=:all: --no-deps`, **Then** все файлы скачаны, `requirements.lock` и `packs.json` записаны, `size_bytes` = сумме `files[].size_bytes`.
2. **Given** win- и linux-сводки, **When** `build-runtime-manifest.py`, **Then** манифест schema 2 содержит записи `format:"wheels"` обеих платформ, URL ведут на официальные CDN.
3. **Given** CI Linux, **When** сборка linux-локов, **Then** torch не устанавливается в venv, а только скачивается; сборка быстрее прежней.

---

### User Story 3 - Пайплайн релиза без `.7z` (Priority: P2)

Windows-фаза: setup/portable/server + win-локи + манифест; CI: linux-локи + tar.gz + `packs-linux.json`; финальная фаза сливает сводки, пересобирает манифест, и `SHA256SUMS` больше не содержит `packs/*.7z`. В `publish-release.ps1` список «packs» заменён на «locks»; лок-артефакты доступны для ревью.

**Why this priority**: релиз — канал доставки фичи; без перестройки пайплайна schema 2 не доедет до пользователя.

**Independent Test**: `publish-release.ps1 -DryRun` перечисляет ассеты без `.7z`, манифест ссылается на колёса CDN; финальная фаза merge берёт `packs-linux.json` и даёт полный манифест обеих платформ.

**Acceptance Scenarios**:

1. **Given** собранные win-локи, **When** Windows-фаза, **Then** ассеты — setup/portable/server/манифест/локи/расширения, ни одного `.7z`.
2. **Given** CI залил linux-артефакты, **When** фаза Final, **Then** `SHA256SUMS.txt` полный и без `packs/*.7z`, манифест содержит обе платформы.

### User Story 4 - Честные размеры и источник в UI (Priority: P2)

Мастер и «Настройки → Компоненты» показывают размер из `size_bytes` (cu128 ≈ 2.56 ГБ, CPU ≈ 114 МБ, argos ≈ 40–80 МБ), источник (PyPI / PyTorch CDN) и ожидаемое время; прогресс — суммарный по всем файлам записи.

**Why this priority**: пользователь принимает решение о загрузке гигабайтов — цифры не должны врать.

**Independent Test**: `/api/runtime` отдаёт `size_bytes` суммы; UI-тест фикстурного ответа показывает «2.56 ГБ» и источник для cu128.

**Acceptance Scenarios**:

1. **Given** запись schema 2, **When** мастер на NVIDIA, **Then** подпись `torch-cu128` содержит честный размер, источник и время.
2. **Given** установка идёт, **Then** прогресс суммирует файлы и сходится к `size_bytes` записи.

---

### User Story 5 - Документация и troubleshooting (Priority: P3)

`docs/APP.md` получает раздел «Компоненты: откуда и сколько» с таблицей и блок «загрузка не пошла»: повтор, где искать лог, своё зеркало через `ILT_RUNTIME_MANIFEST_URL` (с примером); README — короткий абзац «при первом запуске докачиваются компоненты по выбору железа».

**Why this priority**: загрузка на гигабайты с внешних CDN требует честных ожиданий — в стиле гайдов A1111.

**Independent Test**: документы содержат таблицу источников и размеров, шаги повтора, пример переменной манифеста; формулировки совпадают с UI.

**Acceptance Scenarios**:

1. **Given** пользователь без интернета, **When** он читает README/APP.md, **Then** он понимает, что нужно, откуда и сколько скачается, и что делать при сбое.
2. **Given** своё зеркало, **When** `ILT_RUNTIME_MANIFEST_URL` указывает на манифест, **Then** приложение ставит компоненты с него (пример в доке работает).

### Edge Cases

- URL колёса исчез / CDN отдал 403/404 — установка падает с понятной ошибкой, `.part` удаляется; гейт релиза ловит такое до публикации (Tier 1 HEAD).
- Обрыв сети между файлами — повтор доводит установку до конца; уже скачанные и проверенные файлы не перекачиваются без нужды.
- Конфликт путей между колёсами: одинаковое содержимое — пропуск; разное — ошибка, `.tmp` удаляется.
- `files[]` пуст, `size_bytes` не равен сумме, sha256 не 64 hex — запись не ставится, а гейт валит релиз.
- Linux: zipfile не восстанавливает exec-bit — для `.so` не требуется; CI-смоук Linux-деплоя делает `import torch` после установки.
- Манифест недоступен — встроенная копия schema 2; фоновое обновление тянет манифест той же версии приложения (schema 1/2 между версиями не смешиваются).
- Диск кончился при распаковке — `.tmp` удаляется, активации нет; пак остаётся «не установлен».
- Windows без NVIDIA — рекомендация `torch-cpu` не менялась.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Манифест MUST поддерживать schema 2: запись `format:"wheels"` несёт `files[{name, url, sha256, size_bytes}]` (URL — официальные CDN), суммарный `size_bytes` и только per-file sha256; archive-записи сохраняют прежний `sha256` и читаются клиентом для совместимости.
- **FR-002**: MUST существовать генератор локов: `pip download --only-binary=:all: --no-deps -d <stage> --index-url <torch-index | pypi> --extra-index-url https://pypi.org/simple <пины из freeze>` (для argos PyPI — основной индекс, для torch-индексов — страховка; сам `argostranslate` собирается колесом из официального git-пина, т.к. PyPI-релиз жёстко требует stanza→torch, и публикуется одним ассетом релиза в стиле `CLIP_PACKAGE` A1111); результат — колёса, `packs.json` с `files[]` и полный `requirements.lock`, который версионируется в репозитории (`locks/py310-<id>-<os>.lock`, стиль AUTOMATIC1111) и ревьюится в PR; ассетами релиза `requirements.lock` не публикуются; повторный запуск детерминирован.
- **FR-003**: Win-локи MUST собираться на Windows-сборщике, linux-локи — в CI; CI MUST NOT устанавливать torch в venv (только `pip download`); CI MUST проверять воспроизводимость: перегенерация linux-лока совпадает с закоммиченным `locks/`; сводки — `dist/.../packs.json` и `packs-linux.json`, пригодные для merge.
- **FR-004**: `scripts/build-runtime-manifest.py` MUST собирать schema 2 из сводок (merge по `(id, os)`) и писать релизный ассет и встроенную копию; записи schema 2 проходят проверку полноты (сумма, sha256, размеры) до записи.
- **FR-005**: `src/app/runtime.py` MUST скачивать `files[]` по одному с общим прогрессом, сверять sha256 каждого файла до установки, хранить `.part` на файл и удалять его при сбое; скачивание — в фоне, один пак за раз (как сейчас).
- **FR-006**: Распаковка колёс MUST быть пофайловой (без `extractall`): проверка каждого имени на path traversal и абсолютные пути (как в 7z-ветке), порядок — сортировка по имени файла колеса (детерминизм), результат — `runtime/<id>/site-packages`; `.data/scripts` не материализуется; `*.dist-info` и `RECORD` сохраняются.
- **FR-007**: Конфликты путей между колёсами: одинаковое содержимое — пропуск; разное — ошибка установки с удалением `.tmp`; правило покрыто тестом и зафиксировано в спеке.
- **FR-008**: Маркер `pack.json` MUST фиксировать id, version, sha256/список файлов, `installed_at`; активация (`sys.path`, DLL-каталоги) и её порядок не меняются; `py7zr` нужен только archive-ветке.
- **FR-009**: Установка идемпотентна: повторная установка и `--deploy` не перекачивают установленное; повторный запуск после обрыва доводит пак до конца; удаление пака возвращает каталог в исходное состояние.
- **FR-010**: Релизный пайплайн MUST работать со списком «locks» вместо «packs»: Windows-фаза опирается на закоммиченные win-локи и публикует setup/portable/server/расширения + манифест; CI — tar.gz + `packs-linux.json` + `SHA256SUMS-linux.txt` (linux-локи обновляются в репозитории и проверяются на воспроизводимость); `SHA256SUMS` MUST NOT содержать `packs/*.7z`; фаза Final сливает сводки и пересобирает манифест.
- **FR-011**: Гейт публикации MUST иметь Tier 1 — HEAD-проверки всех URL манифеста без скачивания тел (PyPI CDN и PyTorch CDN) с контролем `Content-Length` против `size_bytes` файла и структурную валидацию записи (`size_bytes` = сумме `files[]`, sha256 каждого файла — 64 hex, размеры > 0), — и Tier 2 — установку `torch-cpu` во временный каталог с проверкой `import torch`, кэшируемую в `deep.json` по sha256 входных артефактов (setup/portable/server/манифест), чтобы повторные прогоны не переигрывали её.
- **FR-012**: UI мастера и настроек MUST показывать честный размер из `size_bytes`, источник (PyPI / PyTorch CDN) и ожидаемое время; прогресс MUST суммировать файлы записи и сходиться к `size_bytes`.
- **FR-013**: `docs/APP.md` MUST получить таблицу «Компоненты: откуда и сколько» (CPU ≈ 114 МБ, NVIDIA cu128 ≈ 2.56 ГБ, argos ≈ 40–80 МБ; источник; нужен интернет; прокси) и troubleshooting: повтор, лог, своё зеркало через `ILT_RUNTIME_MANIFEST_URL` с примером; README — короткий блок про первый запуск.
- **FR-014**: Тесты MUST покрывать: генератор локов на фикстуре; детерминизм порядка распаковки; правило конфликтов; полноту `files[]` (sha256, размер > 0, сумма); Linux-смоук `import torch` после установки из колёс.
- **FR-015**: Совместимость: манифест адресуется по версии приложения (`releases/download/v{__version__}/…`), фоновое обновление — манифест той же версии; CLI `--deploy`, портативная раскладка, LAN и окно не меняют контрактов.
- **FR-016**: Локальная сквозная приёмка MUST выполняться до сборки и загрузки релиза: `scripts/e2e-runtime-local.ps1` прогоняет pytest → win-локи → манифест → dev-`--deploy` → frozen portable/server → `publish-release.ps1 -DryRun` + гейт; ошибка любого шага — non-zero и остановка до исправления.
- **FR-017**: Финальный релиз MUST выходить только после зелёной репетиции на теге-кандидате `v1.0.1-rc1` (CI собирает linux-артефакты в draft, `-Phase Final -DryRun` проходит merge); installer/GPU smoke (setup → мастер → cu128 → LaMa на GPU) — на машине разработчика.

### Key Entities

- **Wheelset-запись манифеста**: `id`, `title`, `kind`, `os`, `arch`, `python`, `version`, `format:"wheels"`, `files[{name, url, sha256, size_bytes}]`, `size_bytes` (сумма), `driver_min?`.
- **Archive-запись (совместимость)**: поля schema 1 с одним `sha256` и `url`.
- **Лок-сводка `packs.json`**: записи паков + полный freeze рядом; win- и linux-варианты сливаются по `(id, os)`.
- **Пин-файл лока** (`locks/py310-<os>.lock`): полный freeze платформы, версионируется в репозитории; CI проверяет воспроизводимость перегенерацией.
- **Кэш гейта `deep.json`**: ключ — sha256(setup, portable, server, manifest) → результат глубокой проверки.
- **Маркер `pack.json`**: id, version, sha256/список файлов, `installed_at`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: На чистой машине установка `torch-cu128` из колёс с официальных CDN доводит `resolve_device("auto")` до `cuda`, LaMa считает на GPU; повторный запуск не требует действий.
- **SC-002**: Сборка релиза не производит и не публикует ни одного `.7z`; `SHA256SUMS` без `packs/*.7z`; CI собирает linux-локи без установки torch в venv.
- **SC-003**: Гейт: HEAD-проверки манифеста проходят для PyPI и PyTorch CDN; битая запись (сумма/sha/размер) валит гейт; повторный прогон с теми же входами использует `deep.json`.
- **SC-004**: Размеры и источники в UI и документации совпадают с манифестом (cu128 ≈ 2.56 ГБ вместо прежних «~1.2–1.5 ГБ»); README/APP/troubleshooting описывают первый запуск и сбой загрузки.
- **SC-005**: Полный `pytest` зелёный, `flutter analyze`/`flutter test` зелёные; новые юниты покрывают генератор, распаковку, конфликты и полноту манифеста.
- **SC-006**: До сборки релиза `scripts/e2e-runtime-local.ps1` зелёный: pytest, win-локи, манифест, dev- и frozen-установка `torch-cpu`/`argos` (импорт работает), `publish-release.ps1 -DryRun` и гейт Tier 1/Tier 2.
- **SC-007**: RC-репетиция `v1.0.1-rc1` проходит CI-путь и merge в draft; только после этого собирается и загружается финальный `v1.0.1`.

## Assumptions

- Источники колёс — `files.pythonhosted.org` (PyPI CDN) и `download.pytorch.org`; ретеншн подтверждён (живы даже cu101/cu118/cu121), риск исчезновения URL низкий; страховка — гейт + фиксация версий + переопределение манифеста.
- pip в венве сборки поддерживает `--only-binary`, `--no-deps`, `--index-url/--extra-index-url`, `--platform/--python-version`; torch-индекс отдаёт зависимости (sympy, filelock, typing-extensions, networkx, jinja2), поэтому резолв идёт в один проход.
- Колёса не дублируются ассетами GitHub: пин-файлы локов версионируются в репозитории (`locks/`), релиз публикует манифест и `packs-linux.json`; скачивание идёт с официальных CDN (как в AUTOMATIC1111).
- Argos-пак — официальное git-колесо `argostranslate` (пин коммита, stanza — optional) + колёса стека с PyPI (без torch); собранное колесо публикуется одним ассетом релиза; языковые модели Argos качает сам в `data/argos-packages` (портативно).
- torch 2.11.x (cpu/cu128) под Python 3.10; выпуск `1.0.1` с репетицией на `v1.0.1-rc1`; schema 2 не ломает старые установки — манифест версионирован.
