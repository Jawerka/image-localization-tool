# Feature Specification: Windows Staged Update and Rollback

**Feature Branch**: `codex/046-windows-staged-update`

**Created**: 2026-10-18

**Status**: Implemented

**Input**: Roadmap task T22 requires a Windows update path that stages a candidate, validates it, preserves user data, and restores the previous working release if health validation fails.

## User Scenarios & Testing

### User Story 1 - Обновить установленное приложение (Priority: P1)

Пользователь применяет подготовленный Windows-пакет поверх существующей установки. Обновление проверяет пакет до активации, сохраняет пользовательские проекты и компоненты, а после установки запускает проверку готовности.

**Why this priority**: Без безопасного обновления Windows-пакет нельзя обслуживать без риска потерять рабочую установку или пользовательские данные.

**Independent Test**: Обновить изолированную временную установку с тестовым пакетом, сравнить активную версию и SHA-256 пользовательских каталогов до и после.

**Acceptance Scenarios**:

1. **Given** корректный пакет и закрытое приложение, **When** пользователь запускает обновление, **Then** кандидат проверяется до переключения, становится активным после проверки готовности, а данные остаются прежними.
2. **Given** приложение всё ещё работает, **When** пользователь запускает обновление, **Then** операция завершается понятным сообщением до изменения активной установки.
3. **Given** пакет повреждён или неполон, **When** пользователь запускает обновление, **Then** текущая версия и пользовательские данные не меняются.

### User Story 2 - Восстановить предыдущую версию (Priority: P1)

Если новый пакет не проходит проверку готовности, приложение автоматически возвращается к предыдущей версии. Пользователь также может явно запустить откат к сохранённой версии.

**Why this priority**: Отказ после переключения не должен оставлять приложение неработоспособным.

**Independent Test**: Применить пакет, который намеренно проваливает проверку готовности, затем проверить версию активной установки, доступность сервиса и неизменность пользовательских файлов.

**Acceptance Scenarios**:

1. **Given** предыдущая рабочая версия и кандидат, который не отвечает на проверку готовности, **When** обновление активирует кандидата, **Then** активной снова становится предыдущая версия.
2. **Given** сохранённая предыдущая версия, **When** пользователь запускает явный откат, **Then** версии меняются местами только после успешной проверки готовности.
3. **Given** предыдущей версии нет или она повреждена, **When** пользователь запрашивает откат, **Then** операция отказывает без изменения активной установки.

## Edge Cases

- Недостаточно места для подготовки кандидата: активная установка остаётся нетронутой.
- Обновление или откат уже выполняется: второй процесс не меняет каталоги параллельно.
- Активация не завершилась из-за блокировки файла или отказа файловой системы: предыдущая версия восстанавливается.
- Проверка готовности истекла по времени: кандидат считается неуспешным и выполняется автоматический откат.
- В установке найдены пользовательские данные, которых нет в новом пакете: они остаются доступными после обновления и отката.
- Пакет предназначен для другой платформы или содержит несовпадающие сведения о версии: он отклоняется до активации.

## Requirements

### Functional Requirements

- **FR-001**: Windows-пакет MUST содержать проверяемые сведения о версии, платформе и обязательных файлах приложения.
- **FR-002**: Updater MUST полностью подготовить и проверить кандидата до изменения активной версии.
- **FR-003**: Updater MUST отказаться от операции, если приложение использует файлы целевой установки.
- **FR-004**: Updater MUST сохранять пользовательские каталоги и их содержимое при обновлении и откате.
- **FR-005**: Updater MUST проверять готовность кандидата и ограничивать ожидание установленным тайм-аутом.
- **FR-006**: При неуспешной проверке после активации система MUST автоматически вернуть предыдущую рабочую версию.
- **FR-007**: Пользователь MUST иметь возможность явно запросить откат к сохранённой версии.
- **FR-008**: Одновременно может выполняться только одна операция обновления или отката.
- **FR-009**: Результат операции MUST сообщать активную версию и причину отказа или отката.

### Key Entities

- **Windows release bundle**: Пакет версии приложения, содержащий обязательные части desktop, sidecar и web интерфейса.
- **Active installation**: Установка, которую пользователь запускает в обычном режиме.
- **Previous installation**: Последняя версия, сохранённая для безопасного отката.
- **Shared user data**: Проекты, настройки, модели, runtime-компоненты и другие пользовательские файлы, которые переживают смену версии.

## Success Criteria

### Measurable Outcomes

- **SC-001**: Для 100% корректных тестовых обновлений активируется версия из пакета, а контрольные SHA-256 общих пользовательских файлов остаются неизменными.
- **SC-002**: Для 100% повреждённых пакетов и искусственно проваленных проверок готовности активной остаётся или становится прежняя рабочая версия.
- **SC-003**: Повторный или конкурентный запуск не приводит к двум активным операциям и не повреждает установку.
- **SC-004**: Ошибка проверки готовности обнаруживается не позднее заданного тайм-аута проверки плюс 5 секунд.

## Assumptions

- Updater применяется к распакованному Windows portable layout, создаваемому проектом.
- Приложение должно быть закрыто перед заменой файлов; updater завершает работу с понятным отказом, если процесс ещё работает.
- Пользовательские данные находятся в отдельных каталогах внутри корня установки и переносятся между версиями без преобразования.
- Windows 10/11 и PowerShell 5.1 являются целевым окружением.
