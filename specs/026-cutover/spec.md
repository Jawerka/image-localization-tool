# Feature Specification: Cutover — Flutter-хост как поставляемое приложение

**Feature Branch**: `026-cutover`

**Created**: 2026-10-10

**Status**: Draft

**Input**: Plan (сплит 022–026): 026 — финальный шаг миграции. Поставляемое Windows-приложение становится Flutter-хостом (021–025) и запускает замороженный Python-сайдкар (`--api`) из каталога установки; pywebview-окно остаётся совместимым входом `python -m src.app` (конституция, «Границы совместимости»). Долги, явно отложенные в 026: фокус окна при втором запуске (021 T013 → FR-009), апгрейд Flutter до целевого пина ≥ 3.47.7 (021 FR-015), ручные прогоны канваса/окна (023 T016 остаток, 024 T017), SC-001/SC-002 из 021 (нет orphan-сайдкара за 2 с; холодный старт ≤ 8 с), приёмочный маршрут open → translate → export (025). Контракт API, пайплайн и web-поверхности (расширение, LAN, `--browser`) не меняются.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Установленное приложение запускается как Flutter-хост (Priority: P1)

Пользователь запускает собранное приложение (ярлык/`ImageLocalizationTool.exe`). Открывается нативное Flutter-окно «Image Localization Tool» с оболочкой; консольного окна нет; хост сам поднимает сайдкар из каталога установки, получает handshake и показывает bootstrap (пустой экран/проект). Закрытие окна завершает сайдкар, `api.json` удаляется, процессов Python не остаётся.

**Why this priority**: это и есть cutover: пока поставляемый exe — pywebview-сборка, все 021–025 недоступны в поставке.

**Independent Test**: собрать dist, запустить exe с чистым `ILT_DATA_DIR`: окно — Flutter (drop zone), сайдкар — процесс из dist, REST/SSE работают; закрыть — процессов сайдкара нет, `api.json` исчез. Замер холодного старта ≤ 8 с.

**Acceptance Scenarios**:

1. **Given** чистая сборка dist, **When** приложение запускается, **Then** появляется Flutter-окно с drop zone, консоли нет, `api.json` создан, bootstrap отрисован.
2. **Given** приложение работает, **When** окно закрыто (в т.ч. через диалог выхода), **Then** сайдкар завершён ≤ 2 с, `api.json` удалён, orphan-процессов нет.
3. **Given** референсная машина, **When** измеряется холодный старт, **Then** оболочка готова ≤ 8 с.
4. **Given** пути переданы аргументом (`ImageLocalizationTool.exe page.png` или папка), **When** запуск, **Then** страница/папка попадает в проект (первый экземпляр — импорт, живой — форвард).

---

### User Story 2 - Сборка, раскладка и установщик (Priority: P1)

`scripts/build-windows.ps1` собирает Flutter-релиз и PyInstaller-сайдкар, укладывает раскладку дистрибутива, гоняет smoke; Inno Setup делает установщик, который ставит Flutter-хост ярлыками/Run и не тянет WebView2; `deploy-windows.ps1` зеркалит раскладку в локальную папку приложения. Портативный `data`, модели и раскладка `%APPDATA%`/`%LOCALAPPDATA%` — как у pywebview-сборки.

**Why this priority**: без упаковки US1 негде взять.

**Independent Test**: `build-windows.ps1 -SkipModels` → dist-раскладка проходит smoke; установка из setup.exe на чистом профиле запускается; deploy зеркалит и проверяет целостность.

**Acceptance Scenarios**:

1. **Given** репозиторий с VS 2022 Desktop C++, **When** `build-windows.ps1 -SkipModels`, **Then** в dist лежат Flutter-хост, сайдкар с `_internal`, `web/index.html`, `fonts/`, рантайм Flutter; smoke зелёный.
2. **Given** собранный dist, **When** ставится установщик, **Then** ярлык/Run ведут на Flutter-exe; на машине без WebView2 Runtime установка не скачивает его.
3. **Given** старая установка pywebview-сборки, **When** ставится новая версия, **Then** устаревшие корневые файлы прежней раскладки не остаются рабочей смесью, пользовательские данные (settings, projects, models) сохранены.
4. **Given** `deploy-windows.ps1`, **When** запуск, **Then** папка деплоя содержит хост, сайдкар и `web/`; проверки целостности проходят.

---

### User Story 3 - Второй запуск фокусирует окно (Priority: P2)

Пользователь открывает файл из проводника, когда приложение уже запущено (свёрнуто или за другим окном). Пути уходят живому экземпляру, его окно восстанавливается и выходит на передний план.

**Why this priority**: без фокуса протокол single-instance 021 работает «вслепую»; явно отложено из 021 (T013) под cutover.

**Independent Test**: запустить приложение, свернуть, запустить второй раз с путём → окно восстановлено и в фокусе ≤ 1 с, путь импортирован, второй процесс вышел 0. Механизм — `win32`/`ffi` (единственное расширение зависимостей, обосновать в plan).

**Acceptance Scenarios**:

1. **Given** свёрнутое приложение, **When** второй запуск с путём, **Then** окно восстановлено/в фокусе, путь обработан, второй процесс вышел 0.
2. **Given** второй запуск без путей к живому хосту, **When** срабатывает single-instance, **Then** окно фокусируется и процесс-2 выходит.

---

### User Story 4 - SDK-пин и тесты (Priority: P2)

Flutter-стек обновляется до целевого stable ≥ 3.47.7; пины (`apps/desktop/README.md`, CI, документы 021–026) и `environment.sdk` синхронизированы; `flutter analyze` и `flutter test` зелёные на новом SDK; python/JS-наборы без изменений.

**Why this priority**: пин зафиксирован как условие cutover (021 FR-015); раскладка и фокус проверяются на актуальном SDK.

**Independent Test**: `flutter --version` — целевой stable; analyze+test зелёные; CI windows-latest stable зелёный.

**Acceptance Scenarios**:

1. **Given** обновлённый SDK, **When** `flutter analyze`/`flutter test`, **Then** 0 issues, все тесты проходят.
2. **Given** документация, **When** проверяются пины, **Then** везде один целевой диапазон (stable ≥ 3.47.7), bootstrap-долг снят.

---

### User Story 5 - Приёмочный прогон cutover (Priority: P2)

На собранном приложении проходится маршрут open → translate → правка (канвас/инспектор) → export → exit; LAN-сопряжение после рестарта; первый запуск с пустым data root (мастер); остаток 023 T016 (профиль штрихов маски) — опционально. Результаты — в `tasks.md`.

**Why this priority**: закрывает долги 023/024/025 и SC из 021 на реальной поставке.

**Independent Test**: ручной прогон по чек-листу на dist-приложении; записи в `logs/app.log` и tasks.

**Acceptance Scenarios**:

1. **Given** дистрибутив и тестовая папка, **When** глава открыта, **Then** 2 страницы переведены, правка текста и стиля на канвасе сохраняется, экспорт кладёт файлы в выбранную папку.
2. **Given** чистый data root, **When** первый запуск, **Then** мастер показывается один раз, настройки сохраняются, второй запуск — без мастера.
3. **Given** включённый LAN, **When** сайдкар перезапущен, **Then** статус enabled, код сопряжения выдаётся.

### Edge Cases

- Занятый/битый `api.json` от упавшего прежнего запуска: хост чистит файл перед spawn (021), handshake не подхватывает мёртвый порт.
- Сайдкар отсутствует/изолирован антивирусом: видимое состояние ошибки с Retry (021 FR-005), без тихого зависания.
- Каталог установки без прав на запись: портативный режим не навязывается, данные уходят в `%LOCALAPPDATA%`.
- Апгрейд поверх pywebview-установки: старые корневые `_internal`/exe не должны оставаться активными; при откате на прежнюю версию пользовательские данные не мигрируют.
- Второй запуск при живом хосте, но мёртвом сайдкаре: фокус окна + перезапуск сайдкара (restartSidecar из 025), пути — после готовности.
- Юникод-пути (кириллица) в аргументах, каталоге установки и data root не ломают spawn/handshake.
- Рантайм Flutter несёт свои dll; smoke не требует внешних зависимостей и не зависит от Model/WebView2.
- CI и локальный SDK различаются patch-версией: расхождение допустимо и фиксируется в README (CI ставит актуальный stable).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Дистрибутив MUST поставлять Flutter-хост как основной `ImageLocalizationTool.exe` (окно «Image Localization Tool») без консоли; внутренняя раскладка (папки хост/сайдкар) — на усмотрение плана, но ярлыки и Run установщика MUST указывать на хост.
- **FR-002**: Хост MUST находить и запускать сайдкар из каталога установки без переменных среды (`--api --parent-pid <pid>`); явные `ILT_SIDECAR_EXE`/`ILT_PYTHON` сохраняются для dev и имеют приоритет; отсутствие сайдкара — состояние ошибки с Retry.
- **FR-003**: Завершение хоста (нормальный выход, ошибка, диалог выхода) MUST завершать сайдкар ≤ 2 с и удалять `api.json`; orphan-процессов не остаётся.
- **FR-004**: Холодный старт до отрисованной оболочки с bootstrap MUST быть ≤ 8 с на референсной машине.
- **FR-005**: Портативный режим (`data` рядом с программой), каталог моделей и раскладка `%APPDATA%`/`%LOCALAPPDATA%` MUST разрешаться хостом и сайдкаром одинаково и MUST NOT пересекаться с рантайм-файлами Flutter (его `data`-ассеты не считаются пользовательским каталогом).
- **FR-006**: Запуск с путями MUST доводить их до проекта: первый экземпляр импортирует, живой — принимает форвардом (021 FR-009 сохраняется).
- **FR-007**: Повторный запуск к живому хосту MUST восстанавливать и фокусировать его окно; допускается добавление `win32`/`ffi` — единственное расширение зависимостей 021 FR-014, обоснованное в plan.
- **FR-008**: `scripts/build-windows.ps1` MUST собирать оба бандла (Flutter release + PyInstaller-сайдкар), укладывать дистрибутивную раскладку и прогонять smoke; версия MUST читаться из `src/app/__init__.py` и передаваться Flutter-сборке (`--build-name`/`--build-number`), чтобы свойства exe и версия установщика совпадали.
- **FR-009**: `scripts/smoke_dist.py` MUST проверять новую раскладку: хост-exe, сайдкар-exe с `_internal`, `web/index.html`, `fonts/`, отсутствие `web/mockups`, рантайм Flutter (dll/data); наличие `models/` — по опции сборки.
- **FR-010**: Установщик Inno MUST ставить раскладку и чистить устаревшие файлы прежней (pywebview) раскладки при апгрейде, не затрагивая пользовательские данные; MUST NOT требовать или скачивать WebView2 Runtime.
- **FR-011**: `scripts/deploy-windows.ps1` MUST зеркалить раскладку и проверять целостность (хост, сайдкар, `web/`).
- **FR-012**: Flutter SDK MUST быть обновлён до stable ≥ 3.47.7; пины в `apps/desktop/README.md`, CI и документах синхронизированы; `environment.sdk` обновлён при необходимости; analyze/test зелёные.
- **FR-013**: CI MUST сохранять python/JS/Flutter-джобы зелёными; релизная Windows-сборка и установщик проверяются локально (VS 2022), в CI не входят.
- **FR-014**: `python -m src.app` (pywebview), `--browser`, `--headless`, `--remote`, CLI, расширение и LAN-слушатель MUST остаться совместимыми; `--api`-контракт не меняется.
- **FR-015**: Ручная приёмка MUST покрыть маршрут open → translate → edit → export → exit на собранном приложении, first-run с чистым data root и LAN-сопряжение; результаты (и статус опционального остатка 023 T016) фиксируются в `tasks.md`.

### Key Entities

- **Дистрибутивная раскладка**: каталог установки с хостом, сайдкаром, `web/`, `fonts/`, опционально `models/`; внутренние подкаталоги определяет plan.
- **SidecarCommand**: путь к exe сайдкара + аргументы `--api --parent-pid`; разрешение: env → раскладка → ошибка.
- **Version**: `src/app/__init__.py` — единственный источник; Flutter build-name/build-number и Inno наследуют.
- **DataRoot**: пользовательский `data`/`%LOCALAPPDATA%`; один и тот же для хоста и сайдкара, не пересекается с `data`-ассетами Flutter.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Собранное приложение запускается, показывает Flutter-оболочку и bootstrap; полный маршрут open → translate → export проходит; закрытие не оставляет orphan-сайдкара (провал, если процесс жив > 2 с).
- **SC-002**: Холодный старт ≤ 8 с (не менее двух замеров на референсной машине).
- **SC-003**: `build-windows.ps1` даёт дистрибутив и установщик, smoke и deploy-проверки зелёные; установка на чистый профиль запускается.
- **SC-004**: Второй запуск: окно в фокусе ≤ 1 с, путь обработан, процесс-2 выходит с кодом 0.
- **SC-005**: `flutter analyze` — 0 issues, `flutter test` — все зелёные на SDK ≥ 3.47.7; pytest и JS-наборы без регрессий.
- **SC-006**: Апгрейд поверх старой установки не оставляет работающей смеси раскладок, пользовательские данные сохранены.

## Assumptions

- Целевой пин ≥ 3.47.7 доступен как stable (страница архива Flutter подтверждает релиз ветки 3.47).
- pywebview-совместимость ограничена исходниками: поставляется только Flutter-вход; `python -m src.app` остаётся для dev/legacy (конституция).
- WebView2 установщику не нужен: `--api` не импортирует webview, `--browser` использует системный браузер; блок WebView2 в Inno удаляется вместе с cutover.
- Иконка приложения остаётся стандартной Flutter (кастомной .ico в репозитории нет) — ограничение, не задача.
- Установщик остаётся per-user (`PrivilegesRequired=lowest`, `{localappdata}\Programs`).
- CI ставит актуальный stable канала (без фиксации patch); локальный SDK обновляется до того же stable.
- Модели в дистрибутив по умолчанию не входят (скачиваются первым запуском) — как сейчас.
