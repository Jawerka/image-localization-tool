# Готовые поставки

Два канала используют один пайплайн v2: Linux amd64 CPU-контейнер с браузерным редактором и Windows x64 portable CPU с Flutter-окном. Профиль включает детектор, RapidOCR, LaMa, шрифты, Torch CPU, Argos и языковые модели en↔ru. LLM подключается отдельно. CUDA и ARM не входят в этот профиль.

Начиная с 1.1.0 полные пакеты входят в выпуск. Скачивание — [GitHub Releases](https://github.com/Jawerka/image-localization-tool/releases). Для установки из реестра используйте публичный GHCR и закреплённую версию образа.

## Windows portable CPU full

Распакуйте `ImageLocalizationTool-1.2.0-windows-x64-portable-cpu-full.zip` в доступную на запись папку. Запустите `ImageLocalizationTool/desktop/ImageLocalizationTool.exe`.

Системный Python, установка библиотек и первоначальная загрузка моделей не требуются. Локальные библиотеки Visual C++ находятся также рядом с Flutter EXE. Для RAR/CBR в полном пакете предусмотрены 7z.exe, 7z.dll и лицензия в `tools/7zip`; загрузчик предпочитает их системным распаковщикам. Настройки, проекты, журнал и ключи создаются в `data` рядом с приложением.

Полный ZIP предназначен для новой установки. Для обновления закройте приложение, сохраните старую папку как резервную копию и распакуйте новую версию в чистую папку по прежнему пути программы. Из резервной копии перенесите только `data`, сохраняя работоспособность абсолютных путей оригиналов в проектах. Скрипты staged update из lightweight ZIP нельзя применять к full ZIP: у них иной контракт сохранения компонентов. Сам lightweight portable остаётся прежним каналом.

### Сборка

На Windows-сборщике нужны Python 3.10 с `requirements-release.txt`, PyInstaller, Flutter SDK и 7-Zip. Пользователю приложения эти инструменты не нужны.

```powershell
./scripts/build-windows.ps1 -BuildPython venv-release/Scripts/python.exe
./scripts/package-portable.ps1 -Python venv-release/Scripts/python.exe -FullCpu
```

Дополнительные параметры упаковщика:
- `-ComponentSource <prepared-app>` переиспользует только текущие ревизии ресурсов и runtime CPU/Argos из подготовленной установки. `data`, ключи, проекты и CUDA не копируются. Недостающее устанавливается обычным проверяемым загрузчиком.
- `-ArchiveToolDir <7zip-dir>` задаёт каталог сборочной копии 7-Zip.
- `-UsePreparedStage` повторно использует компоненты `build/portable-full/ImageLocalizationTool`, обновляет код/Flutter/web из актуального dist и проверяет готовность перед ZIP. Личные файлы в staging data приводят к отказу.

```powershell
venv/Scripts/python scripts/smoke-components.py --portable dist/ImageLocalizationTool-1.2.0-windows-x64-portable-cpu-full.zip --prepared
venv/Scripts/python scripts/smoke-portable-desktop.py --app build/frozen-smoke-<digest>/ImageLocalizationTool
```

Первый smoke извлекает ZIP в отдельную папку и проверяет готовность обоих направлений без установки компонентов, затем запускает настоящий pipeline с запрещёнными сетевыми запросами. Второй запускает Flutter с его frozen-sidecar, проверяет начальные настройки, выполняет реальный перевод и экспорт через desktop API. Это проверка запуска окна и интеграции, не ручная визуальная приёмка всех экранов Windows.

## Docker: браузерный редактор

Требуется Linux amd64 Docker Engine с Compose либо совместимая среда Linux-контейнеров на компьютере пользователя. Браузер работает вне контейнера. В образе находятся web, API, worker, CPU-библиотеки и модели; отдельные frontend/DB/queue-контейнеры не нужны.

### Из готового образа

Готовый `ImageLocalizationTool-1.2.0-docker-cpu-full.zip` содержит образ `.tar.gz`, Compose без стадии сборки и README. Распакуйте его и выполняйте команды в этой папке. Исходники и пользовательские данные в пакет не входят.

```sh
docker load -i ImageLocalizationTool-1.2.0-linux-amd64-cpu-full.tar.gz
docker compose up -d --no-build
```

Сборка такого ZIP из уже экспортированного образа:

```powershell
venv/Scripts/python scripts/package-docker.py --image-archive dist/ImageLocalizationTool-1.2.0-linux-amd64-cpu-full.tar.gz
```

Откройте `http://localhost:8080`. Новая схема необязательного входа описана ниже. Ранее опубликованные архивы сохраняют поведение своей версии до обновления образа.

### Доступ к редактору

В актуальных исходниках и локальном обновлении защита **выключена по умолчанию**. Редактор открывается без ключа. Это относится и к установкам со старым `web.token` или `ILT_WEB_TOKEN`: они больше не включают вход автоматически.

Чтобы включить защиту, откройте **Настройки → Доступ**:
1. Укажите логин и новый пароль владельца (10–256 символов).
2. Повторите пароль и включите «Требовать вход по логину и паролю».
3. Нажмите **Сохранить доступ**. Эта кнопка применяет изменения сразу, отдельно от «ОК» и «Отмена» других настроек.

После включения новые браузеры должны войти. Для изменения настроенной учётной записи или отключения защиты введите текущий пароль. Режим и хеш с солью хранятся атомарно в `data/web-access.json` внутри постоянного volume. Сессии отзываются при изменении защиты и перезапуске сервера; срок сессии — 12 часов. Общий проект остаётся один на экземпляр.

Если защита выключена, доступ к редактору имеет любой, кто может открыть его разрешённый адрес. Для недоверенной сети используйте HTTPS. Для резервирования сохраняйте весь `data/`. Если пароль забыт, владелец Docker-хоста может остановить контейнер, сохранить `web-access.json` как резервную копию под другим именем и запустить контейнер: отсутствие файла возвращает явно выбранный открытый режим. Повреждённый файл не отключает защиту, а блокирует запуск до восстановления.

Ранее опубликованные образы со старым входом продолжают использовать `web.token` или `ILT_WEB_TOKEN`. Только для таких образов ключ можно прочитать командой `docker compose exec -T ilt cat /opt/ilt/data/web.token`. Обновление исходников не изменяет уже опубликованные образы в GHCR.

### Из исходников

```sh
docker compose build
docker compose up -d
```

Сеть нужна при сборке для загрузки проверенных зависимостей и моделей. Готовый офлайн-профиль работает без внешней сети. Python-база закреплена digest, транзитивные зависимости базы — `requirements-container.lock`, тяжёлые runtime и ресурсы — существующими каталогами с SHA256. Проверка настоящей страницы входит в Docker build. При изменении кода текущая реализация повторяет подготовку, используя BuildKit-кэш загрузок.

### LAN, порты и авторизация

По умолчанию Compose публикует порт только на localhost. Для LAN задайте, например:

```sh
ILT_PUBLISH_HOST=0.0.0.0 ILT_PORT=18080 ILT_WEB_ORIGINS=http://192.168.88.42:18080 docker compose up -d --no-build
```

Внутри контейнера порт процесса — `ILT_WEB_PORT` (по умолчанию 8080), адрес — `ILT_WEB_BIND` (по умолчанию `0.0.0.0`). Compose публикует этот порт на localhost, пока не задан `ILT_PUBLISH_HOST`.

`ILT_WEB_ORIGINS` — список точных публичных HTTP(S) origins через запятую, с нужным портом. Wildcard, путь и учётные данные не допускаются. Для HTTPS перед reverse proxy укажите внешний HTTPS origin; proxy должен сохранять публичный Host. Приложение не доверяет `X-Forwarded-*`. Для доступа через недоверенную сеть нужен HTTPS на proxy.

Авторизация через существующую HttpOnly/SameSite cookie. Все пользовательские API требуют сессии. `/healthz` сообщает лишь о доступности HTTP, не о качестве/готовности моделей. Это один оператор и общий текущий проект на экземпляр, не многопользовательский сервер.

### Файлы и данные

- В браузере: изображения PNG/JPEG/BMP/TIFF, ZIP/CBZ и проекты .ilt.zip. Для других архивных форматов используйте предварительное преобразование в ZIP/CBZ или desktop-вариант.
- Предел одного файла — 256 МиБ; ZIP — до 10 000 записей и 2 ГиБ распакованного содержимого. Имена файлов не используются как пути клиента. Папки браузера передают главы как метаданные.
- Originals сохраняются в постоянном `data/imports`: ProjectStore хранит пути к ним. Одноимённые архивы распаковываются в независимые пространства.
- Экспорт — ZIP для скачивания. Системная папка клиента не передаётся серверу. Сохранение проекта скачивает .ilt.zip.
- Native dialogs, произвольные серверные пути и установка/удаление runtime через серверный UI запрещены. Новые зависимости доставляются новым образом.
- Compose использует именованный volume в `/opt/ilt/data`. Его нужно сохранять и резервировать. `docker compose down` сохраняет данные; `down -v` удаляет volume.
- Загруженные originals и полученные ZIP/пакеты остаются в данных; автоматическая очистка не реализована. Не удаляйте originals открытых проектов.

Развёрнутый CPU-образ занимает около 4,1 ГБ по измерению Docker Engine. ZIP для загрузки версии 1.2.0 — 1 235 966 432 байта, около 1,15 ГиБ. При обновлении нужно место под старый и новый образы, кэш и пользовательские данные. На тестовом rootfs 20 ГБ несколько промежуточных образов и build cache исчерпали свободное место; удаление только ненужного тестового образа восстановило запуск. Планируйте запас диска и не очищайте тома с проектами вместе с образами.

При обновлении заменяется образ, данные остаются. Старый образ не восстанавливает изменения данных; перед изменением версии сохраняйте резервную копию volume. SIGTERM останавливает worker и сохраняет очередь; незавершённая очередь восстанавливается на паузе.

## Обязательный процесс выпуска

После каждого изменения `main` workflow `.github/workflows/docker.yml` собирает полный CPU-образ из актуального кода, выполняет настоящую обработку с `--network none` и только при успехе публикует `edge-cpu-full`. Это канал разработки.

При выпуске новой версии `scripts/release.ps1 -Prepare` обязательно запускает Linux CI и Docker CI на одном конкретном commit, включает полный Windows CPU ZIP и Docker ZIP в неизменяемый кандидат и сохраняет `GHCR-DIGEST.txt`. Docker workflow проверяет совпадение тега и версии приложения; в образ записываются OCI source/revision/version. Выпуск без полного Docker-пакета и digest отклоняется.

Для пользователей публикуется `ghcr.io/jawerka/image-localization-tool:<version>-cpu-full`. После публикации стабильного GitHub Release автоматически обновляется тег `cpu-full`; опубликованный выпуск не подменяется новым кодом под старой версией. Workflow требует только встроенный `GITHUB_TOKEN` с `packages: write`; личные ключи в исходники и образы не попадают. Публичная видимость пакета задаётся отдельно в настройках GHCR и проверяется анонимным pull.

Готовый [compose.ghcr.yaml](../compose.ghcr.yaml) фиксирует стабильную версию; его нужно скачать как `compose.yaml`. Обновление: резервная копия данных, смена тега версии, `docker compose pull`, затем `docker compose up -d`. Для стабильного окружения не используйте `edge-cpu-full`.
