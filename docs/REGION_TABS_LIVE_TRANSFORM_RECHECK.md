## R1 / T020. P1 — рабочий пайплайн инвалидирует закреплённую раскладку при масштабировании

Код: `src/page_pipeline.py:115`, `:400`, `:418`; `src/components/typesetter.py:174`, `:217`; вызов worker — `src/app/worker.py:1445`.

`PagePipeline.typeset_image` использует стандартный `layout_long_side=2000` и увеличивает небольшие страницы. `_scale_regions` масштабирует bbox и кегли, но не snapshot, его координаты и layout_key. `_frozen_layout` сравнивает старый ключ с уже изменённым регионом и отбрасывает снимок. Финальный рендер снова подбирает строки.

Воспроизведение: белая страница 400×300, dialogue bbox `(80,80,160,75)`, строка `This is a longer sentence for a rotation layout comparison`, Typesetter 10–128/en, подготовка base-layer при 0°, сохранение `_last_layouts[1]` в region.layout_snapshot, поворот на 35°. В `PagePipeline` отключён только auto_stylized_fonts, масштабирование оставлено стандартным.

- До пайплайна snapshot валиден: **кегль 15, 3 строки**.
- Внутри финальной вёрстки: **кегль 66, 4 строки**, layout_key другой.

Кегль 66 находится в увеличенном рабочем пространстве; его нельзя напрямую сравнивать с 15 на исходной странице. Но изменение числа строк с 3 на 4 и несовпадение ключа однозначно показывают повторную раскладку. Worker вызывает этот путь без `_skip_layout_scale=True`.

Исправить: определить пространство координат snapshot и обеспечить согласованную обработку при масштабировании либо выполнять рендер snapshot-регионов в закреплённом пространстве. Проверять через реальный `PagePipeline.typeset_image`, включая worker/apply_document; прямого теста Typesetter недостаточно.

Приёмка: на страницах меньше 2000 px, при изменённом layout_long_side и при нескольких поворотах строки и кегль после обратного масштабирования соответствуют закреплённому snapshot. Отдельно проверить координаты text_position и mesh/quad на том же пути.

## R2 / T021. P1 — web получает snapshot, но Done может отправить документ без него

Код: `web/js/state.js:618–642`, `:675`; `web/js/inspector.js:1137`, `:1235`, `:1246`.

`editDocument` создаёт отдельную копию документа в pendingBody. Позже `rememberLayoutSnapshot` меняет только объект региона текущего state.document. Копия в pendingBody не обновляется. `applyDeferredEdits` отправляет именно её. На desktop есть обновление pendingBody при получении snapshot; в web такого шага нет.

Дополнительный тест использовал существующие fixtures browser/desktop/page и `_open_and_translate` из UI-smoke:

1. Открыть переведённую страницу и выбрать регион.
2. Через реальный `editDocument(..., {deferApply:true})` установить arc и очистить старый layout_snapshot.
3. Дождаться, когда реальный preview вернёт snapshot и он появится в state.document.
4. Вызвать реальный `applyDeferredEdits`, перехватить исходящий PUT.
5. Проверить `PUT.document.regions[0].layout_snapshot`.

Результат: **None**, хотя snapshot уже присутствовал в UI. Assertion упал. Это дефект сохранения, а не отсутствие ручной проверки браузера.

Исправить: синхронизировать производный snapshot с ожидающим сохранения документом либо формировать неизменяемый commit snapshot из актуального состояния после завершения подготовки. Не добавлять отдельный сетевой autosave или лишний Undo только ради производного поля.

Приёмка: реальный preview → Done без промежуточной пользовательской правки; исходящий PUT содержит актуальный snapshot. Дополнительно: Done до завершения preview должен либо дождаться подготовки, либо явно гарантировать эквивалентный серверный snapshot. На сегодня обязательного ожидания актуальной подготовки перед сохранением нет.

## R3 / T022. P1 — повтор после ошибки bake не запускает новую сборку

Код: `apps/desktop/lib/src/state/viewer_state.dart:882–906`; `web/js/state.js:716–741`. Серверный механизм повтора существует отдельно: `POST /api/jobs/retry-errors`, `src/app/server.py:1860`.

После сохранения и ответа status=error клиенты выставляют awaitingBake. Следующее Done при отсутствии нового тела PUT только делает GET страницы. Если worker действительно завершился ошибкой и status остаётся error, повтор снова немедленно завершается ошибкой. Ни новый apply_document, ни retry failed job не запускается.

Существующий Flutter-тест «после ошибки bake повтор не сохраняет заново» возвращает error лишь на первом GET, а на последующих сам возвращает done. Он доказывает способность дождаться внешнего восстановления, но не повторить неуспешную сборку.

Исправить: различать «работа ещё выполняется/связь потеряна» и «job завершился ошибкой». Для первого повторять ожидание, для второго повторно ставить именно нужную сборку нужной версии документа. Не вызывать глобальный retry-errors без оценки области: он может запустить чужие задачи. Нужен адресный и идемпотентный механизм повтора.

Приёмка: реальный или faithful fake worker остаётся в error до команды retry; повтор Done запускает одну новую сборку той же версии, не делает второй PUT документа и доводит результат до готовности.

## R4 / T023. P1 — первая подготовка повёрнутого bend-warp может получить другой source extent

Код: `src/app/server.py:2416–2428`; `src/components/typesetter.py:955–960`.

Для arc/wave/flag/ring с rotation сервер готовит уже повёрнутый слой: временно меняет kind на none и вызывает render_layer с apply_geometry=True. Если входного snapshot ещё нет, `stable` оказывается false. В этом первом ответе выдаётся snapshot, а финальный рендер уже с ним включает stable=True. Получается другая исходная область, от размеров которой зависят warp-формулы.

Изолированный эксперимент: белая страница 600×500, narration bbox `(150,150,160,75)`, текст `This is a longer sentence`, override=18, rotation=35°, kind=none (как после временной замены в `_typeset_base_layer`), capture=True.

- Первый pre-rotated слой без snapshot: **268×255**, origin `(98,60)`.
- Повтор с тем же стилем и snapshot первого вызова: **613×601**, origin `(-75,-112)`.

Обычный вход через none и предварительный preview иногда успевает создать snapshot и скрыть дефект. Это не гарантия: существующий регион может сразу иметь rotation+arc, либо пользователь меняет настройки до окончания первой подготовки.

Исправить: явно выбирать стабильное исходное пространство при первой подготовке независимо от наличия предыдущего snapshot и от применения rotation; финальный render должен использовать тот же контракт. Проверить подготовку без ранее созданного snapshot.

Приёмка: первая и последующие подготовки одного повёрнутого региона имеют одинаковые размеры и origin до применения bend; финальная композиция не меняет деформацию после Done.

## Что пока не следует считать доказанным

- Missing-font тест проверяет сохранение строк и размер страницы, но код подставляет другой доступный шрифт. Snapshot хранит имя файла, а не его fingerprint или glyph raster. Этот тест не доказывает сохранение внешнего вида шрифта при его отсутствии/замене. Нужно выбрать контракт: переносить нужный ресурс, закреплять растр либо явно предупреждать о fallback.
- Mesh/perspective+rotation и skew остались через exact fallback. Web perspective остаётся серверным и без rotation. Это документированное сокращение исходной цели полного мгновенного отклика, а не доказательство её достижения.
- Для arc/wave/flag/ring изменение угла требует серверной подготовки повёрнутого слоя; локальны последующие изменения bend. Это также не полностью локальное вращение композиции.
- Independent final/export сравнение T019 можно автоматизировать. Его не нужно откладывать как проверку, которую «невозможно закрыть кодом»: именно такая интеграционная проверка могла бы выявить R1 до ручной приёмки.
- Сохранение snapshot заголовком без ограничения длины, поведение очень длинного текста, предел 4096 и ресурсы при частичной ошибке тройной подготовки требуют отдельных нагрузочных сценариев. В этом аудите они не объявлены воспроизведёнными дефектами.
