# Аудит состояния проекта — 19 октября 2026

## Вывод

Проект накопил значительный интеграционный и организационный долг. Основная проблема — большие изменения одновременно в одном рабочем дереве, две отдельно развивающиеся реализации интерфейса и отсутствие общего состояния «реализовано → проверено → включено в сборку → поставлено». Удаление старых веток улучшит видимость, но не исправит поведение приложения. Переписывать проект с нуля оснований нет.

Это аудит исходников, истории Git и локальных документов с выборочными запусками тестов. Это не подтверждение качества OCR/перевода на произвольных страницах и не полная приёмка установленной программы. Конкретный пользовательский сбой не воспроизводился: пример симптома и используемая сборка не были заданы.

## Приоритетные находки

### A01 — Высокий: большая часть новой работы не зафиксирована в истории

**Доказательство:** `git status`, `git diff --shortstat`, инвентарь untracked. Новые `src/app/render_cache.py`, `src/components/text_mesh.py`, `web/js/text_mesh.js`, `web/js/mesh_preview_renderer.js`, `web/js/sidebar_tabs.js`, скрипты установки/обновления и specs 036–048 существуют только в рабочем дереве. Основные изменения затрагивают общие `server.py`, `worker.py`, `typesetter.py`, `viewer.js`, `settings.js`.

**Последствие:** название текущей ветки обещает вкладки панели, но фактически дерево содержит инспектор, геометрию текста, кэш, профили установки, deployment и оптимизации. Merge указателей веток эту работу не сохранит; из чистого checkout текущего HEAD она не восстановится. Нельзя надёжно связать регрессию с отдельной фичей или собрать такой же кандидат из одного SHA.

**Действие:** сначала сохранить точный снимок исходников в отдельной интеграционной ветке, явно исключив локальные данные/секреты/модели/логи и агентские служебные материалы. Затем интегрировать проверяемыми блоками. Не начинать с переключений, reset, массового удаления веток или слепого `git add .`.

### A02 — Высокий: две реализации редактора расходятся по возможностям

**Доказательство:** README описывает поставляемый EXE как Flutter, а `python -m src.app` — как WebView2. `apps/desktop/lib/src/ui/shell.dart` использует нативные `ViewerDockHost` и inspector, не загружает `web/index.html` как весь редактор. Спека 026 фиксирует этот cutover. Спеки 036/044/048 и их реализация меняют `web/`; текущий diff не содержит `apps/desktop/lib`.

Конкретные отличия:

- Веб-вкладки «Страницы/Очередь» из 048 созданы в `web/index.html` и `web/js/sidebar_tabs.js`. Flutter `pages_rail.dart:23` по-прежнему строит список и условный `_BatchBlock` в одной колонке.
- Веб-перенос текста пишет `region.text_position` (`web/js/viewer.js:1047`), серверная модель поддерживает поле (`src/models.py:221`). В Flutter исходниках обращений к `text_position` не найдено; `viewer_state.dart` при изменении рамки пишет `region.bbox`. Равенство поведения редакторов не обеспечено.
- Локальный WebGL mesh preview находится в `web/js/mesh_preview_renderer.js`; аналогичная миграция Flutter в текущем изменении отсутствует. Это не доказывает потерю полей при сохранении: Flutter-модель хранит неизвестные поля в raw map. Но одинаковый UX и корректность редактирования новых геометрий требуют отдельной проверки.
- План 044 прямо ограничен web/WebView2, хотя пользовательская формулировка «мастер первого запуска» звучит как возможность всего приложения.

**Последствие:** улучшения можно успешно тестировать в Chromium и не получить их в установленном EXE. Это подтверждённое расхождение поверхностей; связь с конкретным наблюдаемым пользователем сбоем пока гипотеза.

**Действие:** зафиксировать основной редактор для следующей поставки. Если Flutter остаётся основным, переносить только необходимые сценарии с проверкой одинаковых документов. Если основным становится web, нужен отдельный согласованный переход поставки; простой merge этого не сделает. Не поддерживать молчаливое обещание полной эквивалентности.

### A03 — Высокий: доказательства относятся к разным версиям и сборкам

**Доказательство:** исходная версия `src/app/__init__.py` — 1.0.5. Локальный `build/release-candidate.json` описывает 1.0.2 на `43353f7` с `manual_smoke_passed=true`; эта отметка не относится к текущему дереву. `build/build-source.json` содержит другой source hash и пустой список assets. `docs/RELEASE_NOTES_1.0.5.md` отсутствует, есть только 1.0.0–1.0.2. `scripts/release.ps1` при создании нового draft читает notes для текущей версии и требует чистый Git перед запуском Linux CI.

**Последствие:** нельзя считать текущую 1.0.5 проверенной по отметке кандидата 1.0.2. Текущий путь выпуска не подготовлен полностью: dirty-check остановит его, а при создании нового draft потребуются заметки версии. Скрипт Prepare делает дорогие проверки и сборку до dirty-check.

**Действие:** один кандидат = конкретный commit + hash исходников + hashes пакетов + версия + результаты приёмки. Старые отчёты сохранить как историю; не переносить их зелёный статус на новую сборку. Проверку чистоты и наличия notes желательно выполнять до дорогой сборки.

Дополнительное расхождение версии: оба manifest расширения содержат `1.0.1`, тогда как `scripts/build-extension.py` записывает manifest без смены версии, а имя ZIP получает из версии приложения. При текущих исходниках ZIP будет называться `ilt-extension-…-1.0.5.zip`, но внутри останется версия расширения 1.0.1. Это подтверждено чтением пути сборки, новый архив в аудите не создавался. Версию расширения следует либо синхронизировать, либо явно считать независимой и отражать в release metadata. Flutter `pubspec.yaml` тоже содержит 1.0.0, но для него уже есть корректное переопределение `--build-name=$version` в Windows-сборке, поэтому сам по себе этот pubspec не является такой же ошибкой.

### A04 — Высокий: обычный CI не проверяет основные текущие риски

**Доказательство:** `.github/workflows/ci.yml` запускает Python unit без slow/ui/LLM/Argos, JS unit и Flutter analyze/test. В нём нет Chromium UI, интеграционного набора, Windows updater harness и Linux deploy harness. Последний добавлен в `.github/workflows/release.yml:90` — workflow по тегу или ручному запуску.

`tests/e2e/test_ui_smoke.py:1` прямо указывает FakeWorker и отсутствие pywebview. Тесты расширения используют тестовый API. Поэтому зелёный UI suite не подтверждает реальный перевод, качество очистки, чистую установку, WebView2 или Flutter EXE.

**Последствие:** регрессии UI/поставки могут обнаруживаться только после ручного запуска или на релизе. Историческое «607 passed» без команды и границ выборки создаёт излишнюю уверенность.

**Действие:** на PR проверять быстрые сценарии редактора и fake-root Linux deployment; платформенные тяжёлые приёмки держать отдельными, с явным обязательным статусом для выпуска. Числа тестов записывать вместе с командой, средой, commit и ограничениями.

## Реальная очередь: свести к шести потокам

1. **Сохранение и интеграция текущего дерева — первый приоритет.** Итог: воспроизводимый commit, ни один нужный новый файл не потерян, нет локальных данных в истории. Затем одна интеграционная PR/ветка, если искусственное разделение переплетённых изменений слишком рискованно. Чистота истории вторична сохранности работы.
2. **Один основной пользовательский маршрут.** Выбрать целевой UI и пройти открыть → перевести → поправить → сохранить → повторно открыть → экспортировать на той сборке, которой пользуется пользователь. Сначала устранить наблюдаемые сбои этого маршрута; остальные идеи временно не начинать.
3. **Редактор и расширение.** Закончить 048 T004/T005; отдельные приёмки Firefox/Reddit (T06), WebView2 mesh p95/GPU memory и визуальная сверка (039 T001 / T14). Не объединять незавершённое измерение скорости с отсутствием функции.
4. **Чистая установка и восстановление.** T18/T19 и 044 T011: installer/portable, чистый профиль, реальные компоненты, первый перевод, прерывание и перезапуск. Наличие работающего экземпляра CT113 не равно чистой установке.
5. **Deployment и выпуск.** 045 T010, T21/T22: сначала Ubuntu fake-root harness, затем отдельный systemd host с переводом и rollback. Windows updater локально имеет исторические успешные проверки; installer GUI всё ещё отдельно. Подготовить notes и новый единый кандидат после фиксации исходников.
6. **Необязательная оптимизация.** T27: CT113 ONNX threads и последовательность LLM; 023 T016 jank — отложенный профиль. Не блокировать обычный выпуск обещанием ускорения, если он не заявляется в релизе. Сохранять auto по умолчанию до новых измерений.

Эти потоки объединяют дублирующиеся документы, но не отменяют исходные требования. Пока нет воспроизводимой сборки и выбранной основной поверхности, новые фичи из ROADMAP лучше не начинать. Сам ROADMAP корректно называет себя направлениями, не обязательствами: его десять идей не являются десятью долгами.

## Что делать с main и ветками

Сливать все ветки подряд не нужно. В локальном графе нет тридцати разошедшихся реализаций:

- 21 ветка кроме main уже является его предком или совпадает с ним.
- Восемь новых имён указывают на `6e2d742`: `043-preview-compose`, `044-first-run-profiles`, `048-sidebar-tabs`, `codex/035-rectangular-text-layout`, `codex/036-inspector-redesign`, `codex/045-linux-bootstrap-rollback`, `codex/046-windows-staged-update`, `codex/047-incremental-typeset-composition`.
- Между main и HEAD только `c4c4f19 Improve balloon and document text layout` и `6e2d742 Route LAN deploy through PVE jump host`.

На уровне локальной истории это допускает fast-forward main до HEAD, но он включит только два коммита, не 60 изменённых и 119 новых файлов. Поэтому порядок такой:

1. Сохранить текущие исходники с проверкой состава файлов.
2. Получить свежие refs и состояние PR, когда доступен GitHub.
3. Пройти проверки согласованного кандидата и интегрировать его в main.
4. После проверки досягаемости коммитов удалить ненужные локальные имена; удалённые ветки — отдельно с учётом PR и использования.
5. Дальше: один активный блок изменений, короткая ветка, обязательная фиксация завершённого блока. Новую ветку не использовать как замену коммиту предыдущей работы.

Не требуется массовое слияние, удаление specs или переписывание истории. Нужна одна проверяемая линия поставки.
