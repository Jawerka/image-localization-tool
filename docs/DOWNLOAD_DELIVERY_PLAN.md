# План надёжной докачки компонентов

Дата: 2026-10-14. Статус: предложение по результатам изучения проекта, не выполненная реализация.
Цели: небольшая базовая сборка, простой первый запуск, восстановление после сбоев, воспроизводимый релиз двумя действиями: подготовить и опубликовать после ручной приёмки.

## Основа решения

Сохранить PyInstaller-sidecar, Flutter, существующие CLI/HTTP-входы и пайплайн v2. Доработать текущую установку колёс по манифесту. Пользователь не устанавливает Python, Git, pip или CUDA Toolkit и не редактирует переменные окружения.

В базе остаются интерпретатор, библиотеки запуска и интерфейса, код приложения, лицензии, небольшой проверенный шрифт с кириллицей и встроенный каталог компонентов. Докачиваются PyTorch, Argos, языковые модели Argos, детектор, LaMa, ONNX-модели RapidOCR и дополнительные шрифты. Вынос остальных библиотек отдельно оценить по размеру: сокращение базы не должно сделать сам загрузчик зависимым от сети.

Принцип AUTOMATIC1111: фиксировать зависимости и получать их при запуске. Реализацию установки оставить собственной, рассчитанной на frozen-приложение: никаких сборок из исходников и разрешения зависимостей на компьютере пользователя.

## Подтверждённые пробелы текущей реализации

- `runtime._download_files()` удаляет staging перед попыткой, а `download_and_install()` удаляет его в `finally`: скачанные колёса теряются при сбое. Докачки по HTTP Range нет.
- HTTP-ошибки завершают загрузку сразу; 429 и временные 5xx не повторяются автоматически.
- `model_manager` проверяет наличие по ненулевому размеру, без SHA256; URL детектора и части шрифтов используют изменяемый `main`.
- Маркер установленного runtime проверяется поверхностно: наличия `pack.json` и `site-packages` недостаточно для заключения о работоспособности.
- Состояние runtime-задачи хранится в памяти; блокировка не охватывает атомарно весь запуск и не защищает от второго процесса.
- RapidOCR использует пути моделей по умолчанию внутри пакета. Удалить модели из сборки без настройки внешних путей нельзя.
- Argos отдельно получает языковые пакеты через свой индекс в переводчике. Установка Python-компонента Argos ещё не означает готовность перевода.
- Генератор разрешает зависимости заново. Обычный выпуск может неожиданно обновить транзитивные версии.
- Argos привязан к неопубликованному ассету v1.0.1; анонимный HEAD возвращал 404. cu130 пока отсутствует.
- Релизный манифест Windows пересобирается после упаковки; Final добавляет Linux позже. Встроенные и опубликованные данные не гарантированно одинаковы.

## Этап 1. Зафиксировать каталог и отделить зависимости от версии приложения

1. Ввести версионируемый каталог точных артефактов в репозитории: компонент, ревизия, платформа/архитектура/ABI, зависимости, размер загрузки и распаковки, SHA256, основной URL, проверенные запасные URL, происхождение и лицензия. Схему расширить с явной версией; прежние runtime-контракты сохранить адаптером.
2. Идентичность компонента вычислять по полному составу файлов и совместимости. Не считать один и тот же `id` достаточным для пропуска обновления. Версии приложения могут использовать одну ревизию компонентов.
3. Обновление зависимостей — отдельная явная процедура: resolve → проверка → сохранение полных пинов и сводок обеих платформ → ревью. Обычный релиз читает готовые записи; не запускает resolve и не переписывает локи.
4. Argos 1.11.1 взять из уже проверенного колеса, сохранить SHA256 и провенанс. Основной адрес — raw URL публичного репозитория на неизменяемый SHA коммита. Публикация этого коммита предшествует сборке приложения. CI берёт это же колесо; ожидание wheel-ассета в draft удалить.
5. Для крупных файлов оставить официальные источники. Резервные адреса добавлять лишь при наличии реальной копии с тем же SHA256 и прав на распространение. Два адреса GitHub не считать независимыми зеркалами. Собственное зеркало крупных файлов — отдельная инфраструктурная опция, не обязательная часть первого внедрения.
6. Зафиксировать ревизии моделей Hugging Face и шрифтов. Языковые модели Argos включить в каталог поддерживаемых направлений; при обновлении каталога проверять реальные API выбранного колеса.
7. Встроенный каталог полностью достаточен для установки до публикации релиза. Для первой версии не подменять его автоматически удалённым манифестом: это устраняет зависимость от доступности ассета и риск несовместимой подмены. Существующий env override оставить для тестов/администратора, с валидацией совместимости.

## Этап 2. Один надёжный механизм загрузки

Новый общий модуль обслуживает колёса, модели, языковые пакеты и дополнительные шрифты; runtime и model_manager сохраняют свои функции установки.

1. Хранить загрузки в постоянном кэше по SHA256. Проверенные целые файлы переиспользовать; частичные сохранять после обрыва и закрытия приложения. Не удалять успешные файлы из-за сбоя соседнего файла.
2. Продолжать `.part` запросом Range. Проверять 206, Content-Range, начало диапазона и полную ожидаемую длину. При ответе 200 начать файл заново; при 416 проверить готовый файл либо перезапустить его. ETag/If-Range использовать при наличии. После любой загрузки сверять полный SHA256 и размер. Несовпадение удаляет только повреждённый артефакт.
3. Повторять временные сетевые ошибки, 408, 429, 5xx с ограниченным экспоненциальным ожиданием и случайным разбросом; учитывать Retry-After с верхней границей. 404 переводит на следующий проверенный источник; ошибки диска/доступа требуют устранения причины, а не сетевых повторов.
4. После исчерпания попыток переходить в состояние ожидания/ошибки с сохранённым прогрессом. Не делать бесконечных скрытых повторов. Возобновление — автоматически после краткого сбоя или одной кнопкой после длительного.
5. Сохранять очередь, выбранные ревизии, активный файл и состояние задачи. После запуска восстанавливать задачу, проверяя реальные файлы; после переподключения UI читать снимок, не полагаться только на SSE.
6. Блокировать установку межпроцессной блокировкой; создавать задачу атомарно. Параллельный CLI/второе окно не могут писать в одну установку.
7. До загрузки оценивать свободное место отдельно для кэша и места установки: оставшиеся загрузки + распаковка + сохраняемая старая версия + запас. Повторно проверять перед распаковкой. Показывать требуемое место из каталога.
8. По завершении очищать ненужный кэш по политике срока/лимита. Активные и незавершённые задачи исключать из автоматической очистки. Дать действие «Очистить кэш», не удаляющее установленные компоненты.

## Этап 3. Проверяемая установка и восстановление

1. Устанавливать новую ревизию в отдельный временный каталог; защищать распаковку от опасных путей и конфликтов. Не изменять работающую ревизию на месте.
2. Проверять состав установки, затем запускать проверку компонента в отдельном frozen-процессе: импорт PyTorch и маленькая операция; CUDA-операция для GPU; загрузка модели; OCR на маленьком образце; короткий перевод для Argos с языковой моделью.
3. Помечать компонент готовым только после проверки. Если проверка не прошла, сохранять старую работоспособную ревизию; не удалять пользовательские данные.
4. Переключать активную ревизию атомарным указателем/маркером после успешной проверки. Для torch выполнять управляемый перезапуск воркера/sidecar, чтобы не смешивать уже загруженные DLL. Новый процесс повторно проверяет активацию.
5. После аварийного завершения восстанавливать установку по журналу. Неполный временный каталог не активировать; повреждённые компоненты предлагать восстановить, используя кэш.
6. Для обычной Windows-установки хранить скачиваемые данные в доступном пользователю каталоге приложения в LocalAppData. Portable сохраняет данные рядом с приложением, сервер — в явно заданном корне. Разделить install_root и data_root; старые пути читать и мигрировать безопасно, без принудительной перекачки и скрытого переноса гигабайтов.
7. Ограничить изменения существующих публичных CLI/HTTP-контрактов адаптерами; новые настройки добавить в Config с дефолтами.

## Этап 4. Простая подготовка в интерфейсе

1. Мастер спрашивает способ перевода и языки. По ответам вычисляет полный набор необходимых компонентов, включая OCR-фолбэк и языковой пакет. Если в пайплайне остаётся автоматический оффлайн-фолбэк, его зависимости включаются в этот набор заранее; обработка страницы не запускает внезапную сетевую установку.
2. Основное действие — «Подготовить приложение». Показывать общий объём, место на диске, рекомендацию ускорения; cpu/cu128/cu130 и URL оставить в дополнительных настройках.
3. По умолчанию рекомендовать проверенный GPU-пак при совместимом железе. Дать простой вариант «Меньше загрузка, медленнее обработка» для CPU; не скачивать CPU и CUDA одновременно без необходимости.
4. cu130 из исходного плана реализовать в генераторе, каталоге, hardware, deploy и Flutter. Порог драйвера предварительно проверить по документации и frozen-смоуку. Рекомендация драйвера — предварительный выбор; готовность GPU подтверждается реальной CUDA-операцией. Не удалять старый torch до успешной проверки нового.
5. Если GPU-компонент не заработал, предложить CPU одной кнопкой с указанием дополнительного объёма. Не заставлять пользователя разбираться в CUDA и не начинать ещё одну крупную загрузку молча.
6. Показывать этапы «Загрузка», «Проверка», «Установка», «Готово»; скорость/остаток времени оценивать по измерениям, без фиксированного обещания. Поддержать паузу и продолжение.
7. Ошибки объяснять по причине: сеть, место, права, повреждённый файл, несовместимость. Действия: «Продолжить», «Выбрать папку», «Использовать CPU», «Сохранить диагностику». Диагностика без ключей API и секретов.
8. Когда компоненты уже готовы, повторный запуск не требует сети. Если интернет недоступен до завершения подготовки, интерфейс остаётся доступным, показывает недостающие компоненты и позволяет вернуться позже.

## Этап 5. Вынос ресурсов из сборки

1. Убрать ONNX-веса RapidOCR из PyInstaller datas; сохранить требуемые конфигурации и код. В rapid_ocr передавать пути внешних проверенных моделей, запретив неконтролируемое скачивание библиотекой.
2. Детектор и LaMa получать через общий загрузчик; языковые модели Argos устанавливать из проверенного кэша через API Argos. Убрать загрузку языковой модели из выполнения перевода: отсутствующая модель означает необходимость подготовки, а не сетевую операцию внутри обработки.
3. Дополнительные шрифты вынести в каталог компонентов. Один небольшой шрифт с кириллицей оставить в базе для устойчивой вёрстки и отображения до подготовки.
4. Проверка упаковки запрещает torch, argostranslate, основные веса и ONNX-модели RapidOCR в базе. Держать явный список разрешённых базовых ресурсов.

## Этап 6. Простой выпуск для разработчика

Целевой процесс: одна команда подготовки → ручной smoke → одна команда публикации. Названия будущих команд условные: `release.ps1 -Prepare`, `release.ps1 -Publish`.

Подготовка:

1. Проверить версию, заметки, исходный commit, зафиксированные локи/каталог и доступность внешних артефактов.
2. До упаковки собрать окончательный каталог обеих платформ; встроить эти же данные во все сборки. Если компоненты не менялись, использовать существующие записи, не скачивать 2.8 ГБ ради генерации новой сводки.
3. Собрать Windows, расширения и Linux через существующие скрипты/CI; объединить результаты автоматически. Выдавать понятный статус вместо ручных фаз Windows/Final.
4. Проверить комплект, содержимое и контрольные суммы; запустить тесты и установку из готовых frozen-сборок. Кэшировать тяжёлые проверки по составу компонентов и самой сборке; изменившийся sidecar требует новой frozen-проверки.
5. Создать/обновить draft, подготовить пакет для ручной проверки и сохранить отчёт с хэшами файлов. Для локального smoke доступ к зависимости не требует публикации приложения.

Публикация:

1. Проверить тот же набор артефактов, одобренный вручную; ничего не пересобирать и не менять зависимости.
2. Анонимно проверить внешние зависимости, не принимать наличие draft-ассета через API с токеном как доказательство доступности для пользователя. HEAD с длиной полезен, но при неподдерживаемом HEAD выполнить ограниченный GET; SHA256 подтверждать загрузкой/кэшем, не HEAD.
3. Опубликовать draft и проверить публичные ссылки setup/portable/server/метаданных. Повтор команды безопасен; не перезаписывать уже опубликованную версию другим содержимым.

## Приёмка и порядок внедрения

Сначала каталог и воспроизводимость → общий загрузчик → транзакционная установка и пути → вынос ресурсов → мастер → оркестратор релиза. Небольшую правку Argos/raw можно сделать раньше, но она сама не решает устойчивость.

До выдачи пользовательской сборки обязательны автоматические сценарии:

- Разрыв соединения на большом файле, закрытие приложения и продолжение: проверенные файлы не перекачиваются; при поддержке Range продолжается незавершённый файл.
- Сервер игнорирует Range, отдаёт неверный Content-Range, 416, 429, 503, обрывает тело или подменяет байт: нет повреждённой активной установки.
- Основной источник недоступен: проверенный резерв используется автоматически; без резерва задача сохраняется с понятной причиной.
- Нет сети при уже готовых компонентах: запуск и обработка выбранного сценария работают.
- Диск заполнен, каталог недоступен, два установщика запущены одновременно, процесс остановлен при распаковке/переключении: старая рабочая версия сохраняется.
- Чистая frozen-сборка без env override готовит OCR, перевод выбранного направления и LaMa; затем обрабатывает страницу через пайплайн v2. Проверка выполняется в Windows и для серверного Linux.
- Обновление приложения с тем же составом компонентов не вызывает повторную загрузку; portable и обычная установка используют правильные пути.
- CPU проходит проверку на машине без NVIDIA; CUDA проверяется на реальной GPU, включая небольшую операцию и страницу, а не только `cuda.is_available()`.
- Встроенный и релизный каталоги совпадают по содержимому; обычный релиз не переписывает локи и не разрешает зависимости заново.

Сетевые ошибки воспроизводить локальным HTTP-сервером в тестах; не скачивать многогигабайтные колёса для каждого случая. Реальные CDN проверять отдельно при подготовке и публикации.

Перед реализацией оформить новую фичу через Spec Kit: specify → plan → tasks → implement → converge. Изменения требований к сохранению `.part` согласовать с прежней спецификацией 032, которая предписывала очистку при сбоях. Этот документ задаёт предлагаемые решения, но не заменяет формальные артефакты фичи.

## Источники

- Изучены runtime.py, model_manager.py, utils/paths.py, translator.py, rapid_ocr.py, генератор локов, упаковка, публикация, e2e и spec 032.
- AUTOMATIC1111: https://github.com/AUTOMATIC1111/stable-diffusion-webui/blob/master/modules/launch_utils.py — фиксированные зависимости и установка окружения при запуске.
- HTTP Range: https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Range_requests — условия безопасного продолжения загрузки.

Независимое зеркало увеличивает доступность, но требует реального хостинга. Ни raw URL, ни retries не гарантируют работу при полной блокировке всех доступных источников. Основной результат первого внедрения — отсутствие потери прогресса, целостность установки и простое восстановление.
